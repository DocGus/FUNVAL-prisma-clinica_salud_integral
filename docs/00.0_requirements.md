<!-- Registrar el contexto del ejercicio y las necesidades que dieron origen al proyecto. -->1.1 Descripción original
La Clínica Salud Integral requiere centralizar la información relacionada con pacientes, médicos, especialidades y citas médicas mediante una API RESTful.

El sistema se plantea como una solución de backend que permite atender las operaciones principales de recepción, consultorio y gerencia. La API concentra las reglas de acceso, validación y persistencia de la información, y puede servir como base para futuras aplicaciones cliente.

El proyecto contempla las siguientes áreas:
- Recepción: registrar y consultar pacientes, consultar el directorio de médicos y programar citas.
- Consultorio: consultar la agenda correspondiente al médico autenticado y actualizar el estado de sus citas.
- Gerencia: consultar los reportes administrativos protegidos por el rol GERENCIA.
La solución implementada utiliza TypeScript, Express, Prisma 7 y PostgreSQL. La validación de entradas se realiza mediante esquemas Zod; la autenticación utiliza JWT y las contraseñas se protegen mediante bcryptjs. La API cuenta con documentación Swagger.
1.2 Problema y objetivos
- Problema identificado: la administración de pacientes y citas mediante herramientas dispersas dificulta la centralización, consulta y seguimiento de la información.
- Objetivo principal: desarrollar una API RESTful que centralice la información de pacientes, médicos, especialidades y citas de la Clínica Salud Integral.
- Objetivos específicos:
  1. Proporcionar operaciones para registrar y consultar pacientes.
  2. Consultar el directorio de médicos y la información de especialidades.
  3. Programar citas asociando pacientes y médicos existentes.
  4. Consultar la agenda de un médico.
  5. Actualizar el estado de las citas mediante los estados definidos por el sistema.
  6. Consultar reportes administrativos de citas.
  7. Persistir la información en PostgreSQL mediante Prisma.
  8. Validar los datos recibidos antes de procesar las operaciones.
  9. Proteger las operaciones mediante autenticación y autorización por roles.
  10. Documentar los recursos de la API mediante Swagger.

2. Análisis de la idea e identificación de vacíos
<!-- Separar las necesidades del ejercicio de las decisiones que realmente quedaron implementadas. -->2.1 Procesos del sistema
Proceso 1. Registro y consulta de pacientes

El sistema dispone de operaciones para trabajar con los registros de pacientes. Los datos recibidos se validan antes de procesarse y la información se persiste en PostgreSQL mediante Prisma.

Proceso 2. Consulta de médicos y especialidades

La API dispone de recursos para consultar médicos y especialidades. El acceso al directorio de médicos está protegido para los roles definidos en las rutas. La administración completa de médicos o especialidades no se considera parte del alcance confirmado si no existe una operación correspondiente implementada.

Proceso 3. Programación de citas

La programación de una cita requiere identificar un paciente y un médico existentes. El servicio verifica la existencia de ambos registros y rechaza una fecha de inicio anterior al momento actual. Las citas nuevas reciben el estado PROGRAMADA.

Proceso 4. Consulta de agenda

El médico autenticado puede consultar su agenda. El servicio resuelve la relación entre el usuario autenticado y su registro de médico. Cuando se proporcionan los parámetros from y to, se aplica el filtro por rango de fechas; el rango utiliza los límites definidos por la consulta. Los resultados incluyen los datos del paciente y se ordenan por fecha ascendente.

Proceso 5. Actualización del estado de citas

La API permite actualizar el estado de una cita a COMPLETADA o CANCELADA. La operación está protegida y requiere autenticación con el rol correspondiente. El servicio verifica que la cita exista y contempla la relación del médico autenticado con la cita cuando se aplica la comprobación de pertenencia.

Proceso 6. Consulta de reportes

La API incluye un módulo de reportes protegido para el rol GERENCIA. El alcance del ejercicio contempla el volumen de citas agrupadas por especialidad y el corte diario de citas completadas y canceladas. La ejecución funcional de cada reporte debe registrarse en la matriz de pruebas correspondiente.

Proceso 7. Autenticación y autorización

Los usuarios se autentican mediante JWT. Las contraseñas se manejan con bcryptjs y las rutas protegidas aplican middleware de autenticación y autorización por roles. Los roles utilizados por el proyecto son RECEPCIONISTA, MEDICO y GERENCIA.
