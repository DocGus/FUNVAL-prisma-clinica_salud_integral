## 1. Consulta inicial con el cliente

<!-- Obtener la idea original, el contexto y las necesidades del negocio. -->

### 1.1 Descripción original

La Clínica Salud Integral ha administrado durante años su información mediante hojas de cálculo. Este procedimiento ha ocasionado problemas de pérdida de información y cruces de horarios en las citas médicas.

El cliente necesita desarrollar una API RESTful que centralice la información y funcione como núcleo para futuras aplicaciones utilizadas por el personal de recepción, los médicos y la gerencia.

El sistema contempla tres áreas principales:

- **Recepción:** registrar pacientes, consultar médicos, filtrar por especialidad y consultar el expediente de los pacientes con su historial de citas.
- **Consultorio:** programar citas médicas, consultar agendas y actualizar el estado de las citas.
- **Gerencia:** registrar y actualizar médicos y especialidades, crear cuentas de usuario, consultar reportes de citas y obtener cortes diarios.

### 1.2 Problema y objetivos

- **Problema identificado:** La administración de pacientes y citas mediante hojas de cálculo dificulta la centralización y consulta de información, y provoca pérdida de datos y conflictos de horarios.
- **Objetivo principal:** Desarrollar una API RESTful que centralice y permita administrar la información de pacientes, médicos, especialidades y citas de la Clínica Salud Integral.
- **Objetivos específicos:**
  1. Registrar y consultar información de pacientes.
  2. Consultar el directorio de médicos y filtrar sus resultados por especialidad.
  3. Consultar el expediente de un paciente y su historial de citas.
  4. Programar citas médicas asociando pacientes con médicos.
  5. Consultar la agenda de un médico por rango de fechas.
  6. Actualizar el estado de las citas médicas.
  7. Consultar el volumen de citas agrupadas por especialidad.
  8. Obtener un corte diario de citas completadas y canceladas.
  9. Evitar conflictos de horarios entre citas médicas.
  10. Controlar el acceso a las operaciones según el rol del usuario autenticado.
  11. Permitir que GERENCIA administre médicos, especialidades y cuentas de usuario.

### 1.3 Actores involucrados

| Actor | Descripción | Responsabilidad inicial |
|---|---|---|
| Recepcionista | Personal administrativo que atiende a los pacientes. | Registrar pacientes, consultar médicos, consultar expedientes y programar citas. |
| Médico | Profesional encargado de la atención médica. | Consultar su propia agenda y actualizar el estado de sus citas. |
| Gerencia | Personal responsable de supervisar la operación de la clínica. | Administrar médicos, especialidades y cuentas de usuario, y consultar reportes de citas. |
| Sistema | API RESTful que centraliza la información. | Recibir solicitudes, autenticar usuarios, validar datos, aplicar reglas y proporcionar información. |

### 1.4 Funcionalidades esperadas

El cliente espera que el sistema permita:

- Registrar pacientes con sus datos personales.
- Validar que los correos electrónicos tengan un formato correcto.
- Rechazar fechas de nacimiento futuras.
- Evitar registrar dos pacientes con el mismo correo electrónico.
- Registrar médicos con sus datos profesionales y una especialidad.
- Permitir a GERENCIA consultar y actualizar los datos de los médicos.
- Permitir a GERENCIA registrar, consultar y actualizar especialidades.
- Permitir a GERENCIA crear cuentas de usuario y asignarles un rol.
- Vincular cada cuenta MEDICO con un médico existente y permitir como máximo una cuenta por médico.
- Impedir el registro público de cuentas de usuario.
- Evitar registrar médicos con una cédula profesional duplicada.
- Consultar todos los médicos registrados.
- Filtrar médicos por especialidad.
- Consultar el expediente de un paciente con sus datos personales e historial completo de citas.
- Programar una cita para un paciente con un médico específico.
- Establecer una duración fija de 30 minutos por cita.
- Impedir la programación de citas en fechas pasadas.
- Evitar que un médico tenga citas con horarios traslapados.
- Evitar que un paciente tenga dos citas simultáneas con diferentes médicos.
- Permitir citas consecutivas cuando una termina exactamente al comenzar la siguiente.
- Consultar la agenda de un médico dentro de un rango de fechas.
- Cambiar el estado de una cita a COMPLETADA o CANCELADA.
- Registrar las nuevas citas con el estado PROGRAMADA.
- Impedir cambios de estado no permitidos.
- Generar un reporte de volumen total de citas agrupadas por especialidad.
- Generar un corte diario que contabilice las citas COMPLETADAS y CANCELADAS de una fecha específica.
- Proteger las operaciones mediante autenticación y permisos según el rol del usuario.

## 2. Análisis de la idea e identificación de vacíos

### 2.1 Procesos del negocio

**Proceso 1. Registro y consulta de pacientes**

El personal de recepción registra los datos personales del paciente. El sistema valida los campos obligatorios, el formato del correo electrónico, la fecha de nacimiento y la unicidad del correo.

Posteriormente, recepción puede consultar la información del paciente y acceder a su historial completo de citas.

**Proceso 2. Administración y consulta de médicos**
GERENCIA registra y actualiza la información básica y profesional de los médicos. Cada médico debe estar asociado a una sola especialidad existente. RECEPCIONISTA consulta el directorio y filtra resultados por especialidad; MEDICO no puede registrar ni modificar su perfil.
El sistema almacena la información básica y profesional de los médicos. Cada médico debe estar asociado a una sola especialidad existente.
**Proceso 3. Administración de especialidades**
GERENCIA registra, consulta y actualiza el catálogo de especialidades. No se crean especialidades al registrar médicos; cada médico debe asociarse a una especialidad previamente registrada y existente.

**Proceso 4. Programación de citas**

Se selecciona un paciente, un médico y una fecha y hora para programar una cita.

Cada cita tiene una duración fija de 30 minutos. El sistema valida que el paciente y el médico existan, que la fecha no esté en el pasado y que no existan conflictos de horario para ninguno de los dos.

Las citas nuevas se registran con el estado PROGRAMADA.

**Proceso 5. Seguimiento de citas**

Los médicos consultan su propia agenda mediante un rango de fechas y pueden actualizar el estado de sus citas.

Una cita PROGRAMADA puede pasar a COMPLETADA cuando la atención se realiza o a CANCELADA cuando no se llevará a cabo. CANCELADA puede representar una cancelación previa o una inasistencia; el sistema no distinguirá entre ambas causas en el alcance actual.

Las citas COMPLETADA y CANCELADA son estados finales.

**Proceso 6. Consulta de información gerencial**

La gerencia consulta el volumen total de citas agrupadas por especialidad, independientemente de su estado.

También obtiene un corte diario que contabiliza las citas COMPLETADAS y CANCELADAS de una fecha específica, utilizando el calendario de Ciudad de México.

**Proceso 7. Control de acceso y cuentas de usuario**

GERENCIA crea las cuentas de usuario y asigna los roles RECEPCIONISTA, MEDICO o GERENCIA. No existe registro público. La cuenta MEDICO debe estar vinculada a un médico existente y un médico puede tener como máximo una cuenta. Las cuentas de los otros roles no se vinculan con médicos.

Los usuarios deben autenticarse para utilizar las operaciones protegidas. El sistema verifica el rol y limita las operaciones a las responsabilidades correspondientes. La primera cuenta GERENCIA se provisiona mediante inicialización controlada del sistema o de la base de datos; no se expone un endpoint público para crearla. Esta última condición es una decisión técnica de inicialización.

### 2.3 Contradicciones

**Concepto de rentabilidad por área**

El enunciado utiliza el término "rentabilidad por área", pero la funcionalidad descrita solicita únicamente obtener el volumen total de citas agrupadas por especialidad.

No se proporcionan datos de costos, precios, pagos, facturación ni ingresos.

**Interpretación acordada:** El reporte se manejará como volumen de citas por especialidad médica. No se incorporarán funcionalidades financieras.

**Conflictos de horarios**

El problema original menciona cruces de horarios, pero no define cómo detectarlos.

**Interpretación acordada:** No se permitirá que un médico ni un paciente tengan citas con intervalos traslapados. Las citas consecutivas sí estarán permitidas.

### 4.1 Propósito y alcance

- **Propósito:** Desarrollar una API RESTful para centralizar la administración de pacientes, médicos, especialidades y citas de la Clínica Salud Integral.

- **Incluye:**
  - Registro y consulta de pacientes.
  - Validación de datos personales.
  - Validación del formato y unicidad del correo electrónico de pacientes.
  - Validación de fechas de nacimiento.
  - Registro de médicos.
  - Consulta y actualización de médicos por GERENCIA.
  - Validación de unicidad de la cédula profesional.
  - Asociación de médicos con una especialidad.
  - Registro, consulta y actualización del catálogo de especialidades por GERENCIA.
  - Creación de cuentas de usuario y asignación de roles por GERENCIA, sin registro público.
  - Vinculación obligatoria de cuentas MEDICO con médicos existentes y máximo una cuenta por médico.
  - Inicialización controlada de la primera cuenta GERENCIA, sin endpoint público (decisión técnica).
  - Consulta de médicos.
  - Filtrado de médicos por especialidad.
  - Consulta de expedientes de pacientes e historial completo de citas.
  - Programación de citas médicas.
  - Duración fija de citas de 30 minutos.
  - Validación de fechas pasadas.
  - Prevención de traslapes de horarios para médicos y pacientes.
  - Permitir citas consecutivas.
  - Consulta de agendas médicas por rango de fechas.
  - Actualización controlada del estado de las citas.
  - Registro de cancelaciones previas e inasistencias con el estado CANCELADA, sin distinguir la causa.
  - Reporte de volumen de citas por especialidad.
  - Corte diario de citas COMPLETADAS y CANCELADAS.
  - Interpretación de fechas y horarios con la zona horaria America/Mexico_City.
  - Autenticación JWT.
  - Autorización mediante roles.

- **No incluye:**
  - Pagos y facturación.
  - Cálculo de ingresos o rentabilidad financiera.
  - Expedientes clínicos detallados.
  - Recetas médicas.
  - Inventario de medicamentos.
  - Administración de nómina.
  - Control de vacaciones y turnos laborales.
  - Gestión avanzada de disponibilidad semanal.
  - Aplicaciones frontend para los actores.

### 4.2 Actores y procesos

| Actor | Proceso principal |
|---|---|
| Recepcionista | Registro de pacientes, consulta de médicos, filtrado por especialidad, consulta de expedientes y programación de citas. |
| Médico | Consulta de su agenda y actualización del estado de sus citas. |
| Gerencia | Administración de médicos, especialidades y cuentas de usuario; consulta de reportes de volumen por especialidad y cortes diarios. |
| Sistema | Centralización, autenticación, autorización, validación y procesamiento de la información solicitada. |

### 4.5 Reglas y restricciones del negocio

<!-- Documentar las condiciones que deben cumplirse durante la operación del sistema. -->

Las reglas de negocio y sus restricciones se desarrollarán en el documento independiente `01.0_business-rules.md`.

Las condiciones generales confirmadas que deberán formalizarse en ese documento son:

- Los pacientes deben tener un correo electrónico único y válido.
- Las fechas de nacimiento no pueden ser futuras.
- Los médicos deben tener una cédula profesional única.
- Cada médico tendrá una sola especialidad.
- GERENCIA será responsable de administrar médicos y especialidades y de crear cuentas y asignar roles.
- No habrá registro público de usuarios.
- Cada cuenta MEDICO debe vincularse a un médico existente y ningún médico tendrá más de una cuenta.
- Las cuentas RECEPCIONISTA y GERENCIA no requieren vínculo con un médico.
- Cada cita debe estar asociada a un paciente y un médico existentes.
- Cada cita tendrá una duración fija de 30 minutos.
- No se permitirán citas en el pasado.
- No se permitirán traslapes de citas para un mismo médico o paciente.
- Las citas consecutivas estarán permitidas.
- Las citas CANCELADAS no bloquearán horarios.
- CANCELADA puede representar una cancelación previa o una inasistencia; el sistema no distinguirá ni reportará esas causas por separado.
- Toda cita nueva tendrá el estado PROGRAMADA.
- Solo se permitirán las transiciones PROGRAMADA a COMPLETADA y PROGRAMADA a CANCELADA.
- COMPLETADA y CANCELADA serán estados finales.
- Los reportes por especialidad incluirán todos los estados.
- Los cortes diarios considerarán citas COMPLETADAS y CANCELADAS.
- Las operaciones protegidas respetarán los permisos del rol autenticado.

**Nota:** Este documento identifica las restricciones generales. La especificación detallada de condiciones, excepciones y mecanismos técnicos se realizará en `01.0_business-rules.md`.

### 4.6 Resultados y criterios de aceptación

| ID relacionado | Resultado esperado | Criterio de aceptación |
|---|---|---|
| RF-001 | Paciente registrado. | Se registra un paciente cuando proporciona nombre, apellido, correo electrónico y fecha de nacimiento válidos. El teléfono puede omitirse. |
| RF-002 | Validación de datos personales. | Se rechaza un correo con formato inválido o duplicado, y una fecha de nacimiento futura. |
| RF-003 | Médico registrado. | GERENCIA autenticada registra el médico con nombre, apellido, cédula profesional única y una especialidad existente; otros roles reciben HTTP 403. El correo puede omitirse. |
| RF-004 | Directorio de médicos. | RECEPCIONISTA y GERENCIA pueden consultar el listado; si no existen registros, se devuelve una lista vacía. |
| RF-005 | Médicos filtrados. | RECEPCIONISTA y GERENCIA pueden consultar únicamente los médicos que corresponden a la especialidad solicitada. |
| RF-006 | Expediente consultable. | Si el paciente existe, se muestran sus datos personales y todas sus citas. Si no existe, se devuelve HTTP 404. |
| RF-007 | Cita registrada. | Se registra una cita vinculada a un paciente y un médico existentes, con fecha y hora válidas. |
| RF-008 | Fechas pasadas rechazadas. | No se registra una cita cuya fecha y hora de inicio sean anteriores al momento actual. |
| RF-009 | Agenda consultable. | Se muestran las citas del médico cuyo inicio esté dentro del rango solicitado, incluyendo el inicio y excluyendo el final. Si no existen citas, se devuelve una lista vacía. |
| RF-010 | Estado actualizado. | Se permite cambiar una cita PROGRAMADA a COMPLETADA o CANCELADA. Los cambios no permitidos se rechazan con HTTP 409. |
| RF-011 | Reporte por especialidad. | El conteo incluye citas PROGRAMADA, COMPLETADA y CANCELADA, agrupadas por especialidad. |
| RF-012 | Corte diario. | Se contabilizan las citas COMPLETADAS y CANCELADAS correspondientes al día solicitado en la zona horaria de Ciudad de México. |
| RF-013 | Estado inicial de cita. | Toda cita nueva se registra automáticamente como PROGRAMADA, sin permitir que el solicitante elija otro estado inicial. |
| RF-014 | Prevención de traslapes médicos. | Se rechaza una cita si existe otra cita no cancelada del mismo médico cuyo intervalo se traslape. |
| RF-015 | Prevención de traslapes de pacientes. | Se rechaza una cita si el mismo paciente tiene otra cita no cancelada cuyo intervalo se traslape, incluso con otro médico. |
| RF-016 | Citas consecutivas. | Se acepta una cita que comienza exactamente cuando termina otra, siempre que no existan otros conflictos. |
| RF-017 | Estados finales protegidos. | Se rechaza cualquier intento de modificar el estado de una cita COMPLETADA o CANCELADA. |
| RF-018 | Liberación de horarios. | Una cita CANCELADA deja de bloquear el horario del médico y del paciente. |
| RF-019 | Permisos por rol. | RECEPCIONISTA, MEDICO y GERENCIA solo pueden ejecutar las operaciones asignadas a su rol. Un usuario sin autenticación recibe HTTP 401 y uno sin permisos recibe HTTP 403. |
| RF-020 | Fechas y horarios consistentes. | Las consultas de agenda y los cortes diarios utilizan America/Mexico_City como referencia. Los rangos incluyen su inicio y excluyen su final. |
| RF-021 | Especialidad registrada. | GERENCIA autenticada puede registrar una especialidad; se rechaza un nombre duplicado con HTTP 409 y un rol distinto recibe HTTP 403. |
| RF-022 | Catálogo administrado. | GERENCIA autenticada puede consultar y actualizar especialidades existentes; un rol distinto recibe HTTP 403. |
| RF-023 | Datos de médico actualizados. | GERENCIA autenticada puede actualizar los datos de un médico existente sin duplicar la cédula profesional; un rol distinto recibe HTTP 403. MEDICO no puede modificar su propio perfil. |
| RF-024 | Cuenta de usuario creada. | GERENCIA autenticada crea una cuenta con correo único y uno de los roles permitidos; la contraseña se almacena como hash. No existe registro público y un rol distinto recibe HTTP 403. |
| RF-025 | Cuenta MEDICO vinculada. | No se crea una cuenta MEDICO sin asociarla a un médico existente; un médico no puede tener más de una cuenta. RECEPCIONISTA y GERENCIA deben tener doctorId nulo. |

**Criterios generales de respuesta de la API:**

| Situación | Código HTTP esperado |
|---|---|
| Operación correcta | 200 OK o 201 Created, según corresponda. |
| Datos inválidos o campos obligatorios faltantes | 400 Bad Request. |
| Registro inexistente | 404 Not Found. |
| Correo de paciente o usuario, cédula profesional o nombre de especialidad duplicados | 409 Conflict. |
| Traslape de horario | 409 Conflict. |
| Transición de estado no permitida | 409 Conflict. |
| Usuario no autenticado | 401 Unauthorized. |
| Usuario sin permisos suficientes | 403 Forbidden. |
| Consulta correcta sin resultados | 200 OK con una lista vacía. |

La API debe devolver mensajes claros que identifiquen el problema sin exponer información interna de la base de datos.
