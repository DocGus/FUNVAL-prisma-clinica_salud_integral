# 05. Normalización de la base de datos

## Función del documento

Analizar y documentar el proceso de normalización para reducir redundancias innecesarias, evitar anomalías y mejorar la integridad de la información.

La normalización organiza los datos mediante reglas y formas normales. No consiste en dividir tablas arbitrariamente: cada transformación debe justificarse mediante las dependencias funcionales, las claves candidatas y las reglas del negocio.

**Fuente principal:** `04_relation-model.dbml`

**Resultado:** modelo relacional revisado y actualizado, con las transformaciones justificadas.

## Conceptos fundamentales

- **Redundancia:** almacenamiento repetido e innecesario de información.
- **Anomalía de inserción:** dificultad para registrar información sin introducir datos adicionales innecesarios.
- **Anomalía de actualización:** ocurre cuando un dato repetido no se actualiza correctamente en todos sus lugares.
- **Anomalía de eliminación:** al eliminar un registro se pierde información que debería conservarse.
- **Dependencia funcional:** relación donde un atributo o conjunto de atributos determina el valor de otro. Ejemplo: `student_id → student_name`.
- **Clave candidata:** atributo o conjunto mínimo de atributos que identifica de forma única cada registro.
- **Atributo primo:** atributo que forma parte de alguna clave candidata.
- **Atributo no primo:** atributo que no forma parte de ninguna clave candidata.
- **Superclave:** atributo o conjunto de atributos que identifica de forma única cada registro, aunque pueda contener atributos innecesarios.

## 3. Primera Forma Normal (1FN)

Una relación cumple 1FN cuando sus atributos contienen valores atómicos dentro del dominio definido y no existen grupos repetitivos de atributos.

Verificar que:

- Cada celda contenga un valor individual.
- No existan grupos repetitivos de columnas.
- No se almacenen listas en una columna cuando sus elementos deban tratarse como datos individuales.
- Cada registro pueda identificarse mediante una clave.

**Ejemplo incorrecto:**

Almacenar `"Matemáticas, Historia, Inglés"` en una columna `courses` de estudiantes, cuando cada curso debe gestionarse como un dato independiente.

**Posible solución:**

Separar los cursos mediante una entidad relacionada y una estructura de inscripción.

La atomicidad depende del significado del dato y de cómo necesita administrarse. Un texto puede contener muchos caracteres y seguir siendo un valor atómico.

## 4. Segunda Forma Normal (2FN)

Una relación cumple 2FN cuando:

- Cumple previamente 1FN.
- Cada atributo no primo depende de la clave candidata completa.
- No existen dependencias parciales de atributos no primos respecto de una parte de alguna clave candidata.

**Dependencia parcial:** ocurre cuando un atributo no primo depende solamente de una parte de una clave candidata compuesta.

**Ejemplo:**

`Enrollment(student_id, course_id, student_name, course_name, grade)`

Clave candidata: `(student_id, course_id)`

Dependencias:

- `student_id → student_name`
- `course_id → course_name`
- `(student_id, course_id) → grade`

Posible solución:

- `Students(student_id, student_name)`
- `Courses(course_id, course_name)`
- `Enrollments(student_id, course_id, grade)`

La 2FN es especialmente relevante cuando existen claves candidatas compuestas. Una clave candidata de un solo atributo no presenta dependencias parciales respecto a esa clave.

## 5. Tercera Forma Normal (3FN)

Una relación cumple 3FN cuando, para cada dependencia funcional no trivial `X → A`, se cumple al menos una de estas condiciones:

- X es una superclave.
- A es un atributo primo.

En términos prácticos, se busca evitar dependencias transitivas problemáticas de atributos no primos respecto de las claves candidatas.

**Dependencia transitiva:** ocurre cuando un atributo no primo depende de otro atributo no primo, que a su vez depende de una clave candidata.

**Ejemplo:**

`Employees(employee_id, department_id, department_name)`

Dependencias:

- `employee_id → department_id`
- `department_id → department_name`

Posible solución:

- `Employees(employee_id, department_id)`
- `Departments(department_id, department_name)`

La evaluación formal debe considerar todas las claves candidatas y las dependencias funcionales, no solamente la clave primaria elegida.

## 6. Forma Normal de Boyce-Codd (BCNF) — Revisión adicional

BCNF es una forma normal más estricta que 3FN.

**Criterio:**

Para toda dependencia funcional no trivial `X → Y`, X debe ser una superclave.

Se revisa cuando existen relaciones que cumplen 3FN pero todavía pueden presentar dependencias problemáticas, especialmente por varias claves candidatas que se superponen.

No todos los proyectos necesitan transformaciones adicionales a BCNF.

Cuando se proponga una descomposición, se debe revisar:

- Si la descomposición conserva la información sin pérdida.
- Si las dependencias funcionales importantes pueden seguir verificándose.
- Si la nueva estructura sigue representando correctamente las reglas del negocio.

## 9. Consideraciones de desnormalización

La desnormalización introduce redundancia controlada u otras modificaciones en una estructura normalizada para responder a necesidades específicas del sistema.

Ejemplos:

- Almacenar valores agregados para evitar cálculos frecuentes.
- Mantener datos históricos aunque cambie la información original.
- Duplicar información seleccionada para optimizar consultas.

Debe existir una justificación técnica y mecanismos que mantengan la consistencia.

No debe utilizarse para corregir un mal diseño. En proyectos iniciales puede no ser necesaria.
