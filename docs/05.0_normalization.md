# 05. Normalización de la base de datos

## Función del documento

Analizar y documentar el proceso de normalización para reducir redundancias innecesarias, evitar anomalías y mejorar la integridad de la información.

La normalización organiza los datos mediante reglas y formas normales. No consiste en dividir tablas arbitrariamente: cada transformación debe justificarse mediante las dependencias funcionales, las claves candidatas y las reglas del negocio.

**Fuente principal:** `04.0_relation-model.dbml`

**Documentos de referencia:**
- `00.0_requirements.md`
- `01.0_business-rules.md`
- `02.0_entities-and-attributes.md`
- `03.0_diagram-er.md`

**Resultado:** modelo relacional revisado y actualizado, con las transformaciones justificadas.

## Conceptos fundamentales

- **Redundancia:** almacenamiento repetido e innecesario de información.
- **Anomalía de inserción:** dificultad para registrar información sin introducir datos adicionales innecesarios.
- **Anomalía de actualización:** ocurre cuando un dato repetido no se actualiza correctamente en todos sus lugares.
- **Anomalía de eliminación:** al eliminar un registro se pierde información que debería conservarse.
- **Dependencia funcional:** relación donde un atributo o conjunto de atributos determina el valor de otro.
- **Clave candidata:** atributo o conjunto mínimo de atributos que identifica de forma única cada registro.
- **Atributo primo:** atributo que forma parte de alguna clave candidata.
- **Atributo no primo:** atributo que no forma parte de ninguna clave candidata.
- **Superclave:** atributo o conjunto de atributos que identifica de forma única cada registro, aunque pueda contener atributos innecesarios.

## 2. Dependencias funcionales

Identificar las dependencias funcionales entre los atributos de cada relación.

**Representación:**

`A → B`

Significa que el valor de A determina el valor de B.

Una dependencia puede involucrar un atributo o varios atributos que forman una clave compuesta.

Debe derivarse de las reglas del negocio y las características reales de los datos, no solamente de observar algunos registros.

### 2.1 Dependencias identificadas

| Tabla | Determinante | Atributo determinado | Justificación |
|---|---|---|---|
| `patients` | `id` | Todos los demás atributos | El identificador determina los datos del paciente. |
| `patients` | `email` | Todos los demás atributos | El correo es único y obligatorio. |
| `doctors` | `id` | Todos los demás atributos | El identificador determina los datos del médico. |
| `doctors` | `professional_license` | Todos los demás atributos | La cédula profesional es única y obligatoria. |
| `specialties` | `id` | `name` | El identificador determina el nombre de la especialidad. |
| `specialties` | `name` | `id` | El nombre de especialidad es único. |
| `appointments` | `id` | Todos los demás atributos | El identificador determina los datos de la cita. |
| `users` | `id` | Todos los demás atributos | El identificador determina los datos de la cuenta. |
| `users` | `email` | Todos los demás atributos | El correo es único y obligatorio. |

**Dependencia condicional de `users`:**

Para las cuentas con rol `MEDICO`, `doctor_id` identifica como máximo una cuenta:

`doctor_id → user`

Esta dependencia se aplica al conjunto de cuentas vinculadas a médicos. No se considera una clave candidata de toda la tabla `users`, porque `doctor_id` puede ser nulo para las cuentas `RECEPCIONISTA` y `GERENCIA`.

**Consideración adicional:**

La especialidad de un médico se determina mediante `specialty_id`, pero el nombre de la especialidad pertenece a la tabla `specialties`. No se almacena el nombre de la especialidad directamente en `doctors`.

### 2.2 Claves candidatas

Identificar las claves candidatas de cada relación y justificar por qué son únicas y mínimas.

| Tabla | Clave candidata | Justificación |
|---|---|---|
| `patients` | `id` | Identificador único del paciente. |
| `patients` | `email` | El correo es obligatorio y único. |
| `doctors` | `id` | Identificador único del médico. |
| `doctors` | `professional_license` | La cédula profesional es obligatoria y única. |
| `specialties` | `id` | Identificador único de la especialidad. |
| `specialties` | `name` | El nombre de la especialidad es único. |
| `appointments` | `id` | Identificador único de la cita. |
| `users` | `id` | Identificador único de la cuenta. |
| `users` | `email` | El correo de acceso es obligatorio y único. |

**Importante:**

- Una clave candidata debe identificar de forma única cada registro.
- Debe ser mínima: si se elimina cualquiera de sus atributos, deja de identificarlo de forma única.
- Una tabla puede tener más de una clave candidata.
- La clave primaria es una de las claves candidatas seleccionadas.

La columna `users.doctor_id` no se incluye como clave candidata global porque permite valores nulos. Su restricción `UNIQUE` garantiza que un médico no esté asociado a más de una cuenta.

La evaluación de las formas normales debe considerar todas las claves candidatas.

## 3. Primera Forma Normal (1FN)

Una relación cumple 1FN cuando sus atributos contienen valores atómicos dentro del dominio definido y no existen grupos repetitivos de atributos.

Verificar que:

- Cada celda contenga un valor individual.
- No existan grupos repetitivos de columnas.
- No se almacenen listas en una columna cuando sus elementos deban tratarse como datos individuales.
- Cada registro pueda identificarse mediante una clave.

**Ejemplo incorrecto:**

Almacenar varios médicos o varias especialidades en una misma columna cuando cada elemento deba gestionarse como un registro independiente.

**Posible solución:**

Separar las entidades y utilizar relaciones mediante claves foráneas.

La atomicidad depende del significado del dato y de cómo necesita administrarse. Un texto puede contener muchos caracteres y seguir siendo un valor atómico.

### 3.1 Evaluación de 1FN

Las cinco tablas almacenan un valor individual por atributo y no contienen listas ni grupos repetitivos. Cada registro representa una instancia identificable de su entidad.

| Tabla | ¿Cumple 1FN? | Problema identificado | Transformación | Resultado |
|---|---|---|---|---|
| `patients` | Sí | No se identifican listas ni grupos repetitivos. | Ninguna. | Mantiene valores individuales por atributo. |
| `doctors` | Sí | No se identifican listas ni grupos repetitivos. | Ninguna. | Cada médico se registra individualmente. |
| `specialties` | Sí | No se identifican listas ni grupos repetitivos. | Ninguna. | Cada especialidad ocupa un registro independiente. |
| `appointments` | Sí | No se identifican listas ni grupos repetitivos. | Ninguna. | Cada registro representa una cita. |
| `users` | Sí | No se identifican listas ni grupos repetitivos. | Ninguna. | Cada registro representa una cuenta de acceso. |

**Resultado:** las cinco tablas cumplen 1FN. No se requieren transformaciones adicionales.

## 4. Segunda Forma Normal (2FN)

Una relación cumple 2FN cuando:

- Cumple previamente 1FN.
- Cada atributo no primo depende de la clave candidata completa.
- No existen dependencias parciales de atributos no primos respecto de una parte de alguna clave candidata compuesta.

**Dependencia parcial:** ocurre cuando un atributo no primo depende solamente de una parte de una clave candidata compuesta.

En este proyecto, las claves candidatas identificadas están formadas por un solo atributo. Por ello, no existen dependencias parciales respecto de esas claves.

### 4.1 Evaluación de 2FN

Todas las claves candidatas identificadas son simples. Por ello, ninguna tabla puede tener dependencias parciales respecto de una parte de una clave compuesta.

| Tabla | Claves candidatas simples | Dependencia parcial | Transformación | Resultado |
|---|---|---|---|---|
| `patients` | `id` y `email` (por separado) | No identificada. | Ninguna. | Cumple 2FN. |
| `doctors` | `id` y `professional_license` (por separado) | No identificada. | Ninguna. | Cumple 2FN. |
| `specialties` | `id` y `name` (por separado) | No identificada. | Ninguna. | Cumple 2FN. |
| `appointments` | `id` | No identificada. | Ninguna. | Cumple 2FN. |
| `users` | `id` y `email` (por separado) | No identificada. | Ninguna. | Cumple 2FN. |

**Resultado:** todas las tablas cumplen 2FN porque sus claves candidatas son simples y no presentan dependencias parciales.

## 5. Tercera Forma Normal (3FN)

Una relación cumple 3FN cuando, para cada dependencia funcional no trivial `X → A`, se cumple al menos una de estas condiciones:

- X es una superclave.
- A es un atributo primo.

En términos prácticos, se busca evitar dependencias transitivas problemáticas de atributos no primos respecto de las claves candidatas.

**Dependencia transitiva:** ocurre cuando un atributo no primo depende de otro atributo no primo, que a su vez depende de una clave candidata.

### 5.1 Evaluación de 3FN

En cada tabla, las dependencias funcionales globales documentadas tienen como determinante una clave candidata. La unicidad de `users.doctor_id` se limita al subconjunto de cuentas `MEDICO` y no se considera una dependencia global. No se identifican dependencias transitivas entre atributos no primos que requieran descomposición.

| Tabla | Dependencia identificada | ¿Cumple 3FN? | Transformación | Resultado |
|---|---|---|---|---|
| `patients` | `id → first_name, last_name, email, birth_date, phone`; `email → id, first_name, last_name, birth_date, phone` | Sí | Ninguna. | No se identifican dependencias transitivas problemáticas. |
| `doctors` | `id → first_name, last_name, professional_license, email, specialty_id`; `professional_license → id, first_name, last_name, email, specialty_id` | Sí | Ninguna. | Los datos de especialidad se mantienen en su tabla independiente. |
| `specialties` | `id → name`; `name → id` | Sí | Ninguna. | No se identifican dependencias transitivas. |
| `appointments` | `id → patient_id, doctor_id, start_at, status` | Sí | Ninguna. | Los datos del paciente y del médico se consultan mediante sus referencias. |
| `users` | `id → email, password_hash, role, doctor_id`; `email → id, password_hash, role, doctor_id`; para cuentas MEDICO, `doctor_id → id, email, password_hash, role` (condicional) | Sí | Ninguna. | Los datos profesionales del médico no se duplican en la cuenta. |

En cada celda con varias dependencias, cada determinante se evalúa por separado; no representa una clave compuesta.

**Ejemplo de separación correcta:**

En lugar de almacenar el nombre de la especialidad en cada médico:

- `doctors.specialty_id` referencia `specialties.id`.
- `specialties.name` almacena el nombre de la especialidad.

Esto evita que el mismo nombre se repita en todos los registros de médicos que pertenecen a una especialidad y reduce anomalías de actualización.

**Consideración:** la evaluación se basa en las dependencias funcionales establecidas por las reglas del negocio. No se han definido otras dependencias entre atributos que justifiquen nuevas descomposiciones.

**Resultado:** las cinco tablas cumplen 3FN bajo las dependencias funcionales documentadas.

## 6. Forma Normal de Boyce-Codd (BCNF) — Revisión adicional

BCNF es una forma normal más estricta que 3FN.

**Criterio:**

Para toda dependencia funcional no trivial `X → Y`, X debe ser una superclave.

Se revisa cuando existen relaciones que cumplen 3FN pero todavía pueden presentar dependencias problemáticas, especialmente por varias claves candidatas que se superponen.

No todos los proyectos necesitan transformaciones adicionales a BCNF.

Cuando se proponga una descomposición, se debe revisar:

- Si la descomposición conserva la información sin pérdida.
- Si las dependencias funcionales importantes pueden seguir verificándose.
- Si la nueva estructura sigue representando correctamente las reglas del negocio.

### 6.1 Evaluación de BCNF

Se revisan los determinantes de las dependencias funcionales documentadas, incluidas las claves candidatas alternativas. Cada determinante global es una superclave; no se identifica una descomposición necesaria.

| Tabla | Dependencia | ¿El determinante es superclave? | Transformación | Resultado |
|---|---|---|---|---|
| `patients` | `id → atributos` y `email → atributos` | Sí, en ambos casos. | Ninguna. | Cumple BCNF. |
| `doctors` | `id → atributos` y `professional_license → atributos` | Sí, en ambos casos. | Ninguna. | Cumple BCNF. |
| `specialties` | `id → name` y `name → id` | Sí, en ambos casos. | Ninguna. | Cumple BCNF. |
| `appointments` | `id → atributos` | Sí. | Ninguna. | Cumple BCNF. |
| `users` | `id → atributos` y `email → atributos` | Sí, en ambos casos. | Ninguna. | Cumple BCNF bajo las dependencias documentadas. |

**Nota sobre `users.doctor_id`:**

La unicidad de `doctor_id` se aplica a los valores no nulos. La dependencia funcional correspondiente se considera para el subconjunto de cuentas con rol `MEDICO`, no como una dependencia global que convierta `doctor_id` en clave candidata de toda la relación.

**Resultado:** no se identifican dependencias funcionales no triviales cuyo determinante no sea superclave. No se requieren transformaciones adicionales para alcanzar BCNF bajo las reglas documentadas.

## 9. Consideraciones de desnormalización

La desnormalización introduce redundancia controlada u otras modificaciones en una estructura normalizada para responder a necesidades específicas del sistema.

Ejemplos:

- Almacenar valores agregados para evitar cálculos frecuentes.
- Mantener datos históricos aunque cambie la información original.
- Duplicar información seleccionada para optimizar consultas.

Debe existir una justificación técnica y mecanismos que mantengan la consistencia.

No debe utilizarse para corregir un mal diseño. En proyectos iniciales puede no ser necesaria.

### 9.1 Necesidades identificadas

El sistema requiere consultar:

- Expedientes de pacientes con historial de citas.
- Agendas médicas por rango de fechas.
- Reportes de citas agrupadas por especialidad.
- Cortes diarios de citas completadas y canceladas.

Estas consultas pueden resolverse mediante relaciones, filtros, agrupaciones e índices, sin duplicar información de las entidades.

### 9.2 Decisiones de desnormalización

| Elemento | Redundancia introducida | Justificación | Mecanismo de consistencia |
|---|---|---|---|
| Modelo completo | Ninguna. | No se identifican necesidades actuales que justifiquen duplicar información. | Se conservan las relaciones normalizadas y sus claves foráneas. |

**Decisión:**

No se identificaron necesidades que justifiquen desnormalización en esta etapa.

Los índices propuestos en `appointments` no representan desnormalización: son estructuras de acceso que no duplican atributos de negocio dentro de las relaciones.
