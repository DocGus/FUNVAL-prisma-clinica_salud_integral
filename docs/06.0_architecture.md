## 7. Seguridad, autenticación y autorización

### 7.1. Autenticación mediante JWT

La API utiliza JSON Web Token para identificar a los usuarios autenticados.

El flujo general es:

1. El usuario envía sus credenciales al endpoint de inicio de sesión.
2. El servicio de autenticación consulta la cuenta.
3. Se verifica la contraseña mediante bcryptjs contra el hash almacenado.
4. Si las credenciales son válidas, se genera un JWT.
5. El cliente envía el token en el encabezado `Authorization: Bearer <token>`.
6. El middleware verifica el token antes de permitir el acceso a las rutas protegidas.

La clave de firma se administra mediante variables de entorno y no debe incluirse en el repositorio.

### 7.2. Autorización basada en roles

Los roles definidos en el esquema son `RECEPCIONISTA`, `MEDICO` y `GERENCIA`.

Las restricciones de acceso confirmadas en las rutas revisadas son:

| Funcionalidad | RECEPCIONISTA | MEDICO | GERENCIA |
|---|---:|---:|---:|
| Programar citas | Sí | No | No confirmado |
| Consultar directorio médico | Sí | No confirmado | No confirmado |
| Consultar agenda de médico | No | Sí, con pertenencia | No |
| Actualizar estado de cita | No | Sí, con pertenencia | No |
| Consultar reportes | No | No | Sí |

Esta tabla no constituye una matriz exhaustiva de todos los recursos. Los permisos de pacientes y especialidades deben documentarse a partir de sus middlewares y rutas concretas, sin inferirlos únicamente por el nombre del rol.

### 7.3. Autorización por pertenencia del recurso

Para las operaciones de agenda y actualización de citas realizadas por médicos, la autorización por rol se complementa con la comprobación de pertenencia.

El flujo revisado contempla:

- Obtener el `doctorId` asociado a la cuenta autenticada.
- Verificar que el usuario tenga el rol MEDICO y una asociación válida con un registro Doctor.
- Restringir la consulta de agenda al médico autenticado.
- Comprobar la pertenencia de la cita al médico autenticado al actualizar su estado.

La comprobación evita que un médico opere sobre la agenda o las citas de otro médico.

### 7.4. Protección de contraseñas y datos

Las contraseñas se almacenan mediante hashes y se verifican con bcryptjs; no deben almacenarse en texto plano.

Las variables de entorno, claves y credenciales deben mantenerse fuera del control de versiones.

El acceso a los recursos protegidos se controla mediante autenticación y autorización en las rutas correspondientes. La revisión de este documento no sustituye una auditoría integral de privacidad ni permite afirmar que exista un expediente clínico ampliado.
