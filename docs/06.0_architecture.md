# 06.0 — Arquitectura del sistema
# Backend Persistente con Prisma — Clínica Salud Integral

## 1. Objetivo de la arquitectura

Definir la arquitectura técnica de la API RESTful de Clínica Salud Integral, estableciendo los componentes que se construirán, sus responsabilidades, la organización del código y la forma en que interactuarán para satisfacer los requerimientos funcionales y las reglas de negocio previamente documentadas.

La solución utilizará una arquitectura MVC modular, complementada con una capa de servicios para implementar las reglas de negocio y coordinar las operaciones que involucren varias entidades.

El sistema estará construido con:

- Node.js y TypeScript como entorno de ejecución y lenguaje de programación.
- Express 5 como framework para la API HTTP.
- PostgreSQL como sistema gestor de base de datos.
- Prisma ORM 7 como herramienta de modelado y acceso a datos.
- Zod para validar los datos recibidos.
- JWT para autenticación.
- bcryptjs para el almacenamiento seguro de contraseñas.
- Vitest y Supertest para pruebas automatizadas.
- Swagger UI y OpenAPI para documentar y probar los endpoints.

La arquitectura deberá permitir que las futuras aplicaciones de recepción, consultorio y gerencia consuman los servicios de la API sin acceder directamente a la base de datos.

## 2. Alcance arquitectónico

### 2.1. Componentes que se construirán

El backend estará organizado en los siguientes componentes:

| Componente | Responsabilidad |
|---|---|
| API HTTP | Recibir solicitudes y entregar respuestas mediante endpoints REST. |
| Rutas | Definir los endpoints y asociarlos con sus respectivos middlewares y controladores. |
| Middlewares | Ejecutar autenticación, autorización, validaciones y tratamiento transversal de solicitudes. |
| Controladores | Recibir las solicitudes, coordinar la ejecución de los servicios y construir las respuestas HTTP. |
| Servicios | Implementar reglas de negocio y coordinar operaciones que requieren validaciones o múltiples consultas. |
| Modelos | Encapsular las operaciones de persistencia mediante Prisma Client. |
| Base de datos | Almacenar pacientes, médicos, especialidades, citas y cuentas de usuario. |
| Configuración | Administrar variables de entorno, conexión a PostgreSQL y configuración general. |
| Pruebas | Verificar el comportamiento de los componentes y los flujos de la API. |
| Documentación | Describir los endpoints y facilitar su consumo mediante Swagger UI. |

### 2.2. Funcionalidades contempladas

La API se dividirá en cuatro módulos funcionales:

1. **Recepción:** administración de pacientes, consulta de expedientes y directorio médico.
2. **Consultorio:** programación de citas, consulta de agenda y actualización de estados.
3. **Gerencia:** administración de médicos, especialidades, cuentas de usuario y consulta de reportes.
4. **Autenticación y autorización:** inicio de sesión, emisión de JWT y control de acceso según rol y pertenencia del recurso.

### 2.3. Límites de la solución

La arquitectura contempla exclusivamente el backend de la aplicación.

No se desarrollará una interfaz gráfica de usuario. Las aplicaciones de recepción, médicos y gerencia serán clientes externos que consumirán la API.

La solución tampoco incorporará módulos financieros, pagos, facturación ni funcionalidades ajenas a los requerimientos establecidos.

## 3. Estilo arquitectónico y organización general

### 3.1. Arquitectura MVC modular con capa de servicios

Se utilizará el patrón MVC como estructura principal, incorporando una capa de servicios para separar las reglas de negocio de las operaciones HTTP y del acceso a datos.

La organización tendrá cinco responsabilidades principales:

- **Routes:** definen los endpoints y conectan las solicitudes con los controladores.
- **Middlewares:** procesan las solicitudes antes de llegar al controlador.
- **Controllers:** administran la comunicación HTTP.
- **Services:** ejecutan las reglas de negocio y coordinan las operaciones.
- **Models:** interactúan con PostgreSQL mediante Prisma Client.

Esta separación evita concentrar toda la lógica en los controladores y permite probar las reglas de negocio independientemente de Express.

### 3.2. Flujo general de arquitectura

```text
                  CLIENTE HTTP
                       |
                       v
                 EXPRESS SERVER
                       |
                       v
                    ROUTES
                       |
                       v
                   MIDDLEWARES
              /         |          \
             /          |           \
        JWT Auth    Authorize      Zod
             \          |           /
              \         |          /
                       v
                  CONTROLLERS
                       |
                       v
                    SERVICES
                       |
              Reglas de negocio
              Validaciones
              Coordinación
              Transacciones
                       |
                       v
                     MODELS
                       |
                       v
                  PRISMA CLIENT
                       |
                       v
                   POSTGRESQL
```

El flujo de respuesta seguirá el camino inverso: el resultado de la operación regresará al controlador, que construirá la respuesta HTTP correspondiente.

### 3.3. Responsabilidades y límites de cada capa

| Capa | Puede realizar | No debe concentrar |
|---|---|---|
| Routes | Definir métodos HTTP, URLs y middlewares. | Reglas de negocio o consultas SQL. |
| Middlewares | Autenticar, autorizar y validar solicitudes. | Operaciones completas del dominio. |
| Controllers | Leer parámetros, invocar servicios y responder. | Consultas complejas o reglas de negocio extensas. |
| Services | Aplicar reglas, coordinar modelos y transacciones. | Construcción directa de respuestas HTTP. |
| Models | Ejecutar consultas y operaciones con Prisma. | Decisiones de autorización o respuestas HTTP. |

## 5. Modelo de datos y persistencia

### 5.1. Sistema gestor de base de datos

Se utilizará PostgreSQL como base de datos relacional.

Prisma ORM 7 será el mecanismo principal para interactuar con la base de datos, generar tipos a partir del esquema y administrar las migraciones.

El esquema de Prisma será la representación técnica del modelo relacional definido en los documentos anteriores.

### 5.2. Entidades persistentes

La base de datos tendrá cinco modelos principales:

| Modelo | Responsabilidad |
|---|---|
| Patient | Almacenar información personal de los pacientes. |
| Doctor | Almacenar información profesional de los médicos. |
| Specialty | Mantener el catálogo de especialidades médicas. |
| Appointment | Registrar las citas y su estado. |
| User | Administrar las cuentas de acceso y sus roles. |

Las relaciones principales serán:

- Una especialidad puede estar asociada con varios médicos.
- Un médico pertenece a una especialidad.
- Un paciente puede tener varias citas.
- Un médico puede atender varias citas.
- Cada cita pertenece a un paciente y a un médico.
- Una cuenta con rol MEDICO está vinculada a un médico existente.
- Un médico puede tener como máximo una cuenta de acceso.

### 5.3. Acceso a datos mediante Prisma

Los modelos serán responsables de encapsular las operaciones de persistencia utilizando Prisma Client.

Se utilizarán las operaciones correspondientes a cada necesidad:

| Operación | Prisma Client |
|---|---|
| Crear registros | `create()` |
| Consultar listas | `findMany()` |
| Consultar un registro | `findUnique()` / `findFirst()` |
| Actualizar registros | `update()` |
| Consultar relaciones | `include` / `select` |
| Agrupar información | `groupBy()` |
| Ejecutar consultas SQL parametrizadas | `$queryRaw` |

Los controladores y servicios no deberán crear conexiones independientes a PostgreSQL. Se utilizará una instancia compartida de Prisma Client, configurada mediante el driver adapter de PostgreSQL.

### 5.4. Migraciones y generación del cliente

El archivo `prisma/schema.prisma` será la definición del esquema de persistencia.

Los cambios estructurales se aplicarán mediante migraciones de Prisma. El cliente generado se utilizará para obtener acceso tipado a los modelos y operaciones disponibles.

Las migraciones deberán conservarse bajo control de versiones para mantener sincronizados el esquema y la base de datos de los distintos entornos.

La configuración del CLI utilizará el nombre estándar `prisma.config.ts`, que Prisma descubre automáticamente. Si se conserva un nombre alternativo, como `prisma7.config.ts`, los scripts que ejecuten Prisma deberán indicar explícitamente `--config prisma7.config.ts`.

### 6.1. Convenciones generales

La API utilizará:

- Prefijo general `/api`.
- Métodos HTTP según la operación solicitada.
- JSON como formato principal de intercambio.
- Identificadores para consultar y modificar recursos.
- Códigos HTTP para comunicar resultados y errores.
- Validación de parámetros, query strings y cuerpos de solicitudes.

## 7. Seguridad, autenticación y autorización

### 7.1. Autenticación mediante JWT

Se utilizará JSON Web Token para identificar a los usuarios autenticados.

El flujo de autenticación será:

1. El usuario envía sus credenciales al endpoint de inicio de sesión.
2. El servicio de autenticación consulta la cuenta mediante su correo electrónico.
3. Se compara la contraseña recibida con el hash almacenado mediante bcryptjs.
4. Si las credenciales son válidas, se genera un JWT.
5. El cliente utiliza el token en el encabezado `Authorization: Bearer <token>`.
6. El middleware de autenticación verifica el token antes de permitir el acceso a las rutas protegidas.

El token incluirá la identificación del usuario, su correo y su rol.

La clave de firma se almacenará en una variable de entorno y nunca se incluirá en el repositorio.

### 7.2. Autorización basada en roles

Se implementará un middleware que permita o deniegue el acceso según el rol del usuario autenticado.

| Funcionalidad | RECEPCIONISTA | MEDICO | GERENCIA |
|---|---:|---:|---:|
| Registrar pacientes | Sí | No | No |
| Consultar pacientes y expedientes | Sí | No | No |
| Consultar directorio médico | Sí | No | Sí |
| Registrar y actualizar médicos | No | No | Sí |
| Consultar y administrar especialidades | Consulta | No | Sí |
| Crear cuentas y asignar roles | No | No | Sí |
| Programar citas | Sí | No | No |
| Consultar agenda propia | No | Sí | No |
| Actualizar estado de sus citas | No | Sí | No |
| Consultar reportes | No | No | Sí |

La autorización se aplicará mediante middlewares en las rutas protegidas.

### 7.3. Autorización por pertenencia del recurso

La autorización por rol no será suficiente para las operaciones de los médicos.

Además, el sistema verificará que el médico autenticado sea propietario de la agenda o de la cita que intenta consultar o modificar.

Para ello:

- La cuenta del médico tendrá una relación con el registro correspondiente en `doctors`.
- El servicio obtendrá el `doctorId` asociado a la cuenta autenticada.
- Las consultas de agenda estarán restringidas a ese identificador.
- La actualización del estado de una cita comprobará que la cita pertenece al médico autenticado.

Si el recurso pertenece a otro médico, se responderá con HTTP 403.

### 7.4. Protección de contraseñas y datos

Las contraseñas nunca se almacenarán en texto plano.

Se utilizará bcryptjs para generar y verificar hashes de contraseñas.

Las variables de entorno, claves y credenciales se mantendrán fuera del control de versiones.

El acceso a los expedientes médicos estará restringido según las responsabilidades definidas para cada rol.

## 8. Validaciones y reglas de negocio

### 8.1. Validación de solicitudes

Se utilizará Zod para validar los datos recibidos antes de ejecutar las operaciones correspondientes.

Las validaciones se dividirán en:

- Validación de estructuras y tipos de datos.
- Validación de campos obligatorios.
- Validación de formatos.
- Validación de parámetros de ruta y query strings.
- Validaciones que dependan de información de la base de datos.

Los esquemas Zod estarán organizados por módulo y serán utilizados mediante middlewares.

### 8.2. Reglas de negocio en la capa de servicios

Las reglas de negocio se implementarán principalmente en los servicios.

Entre las validaciones que deberán realizarse se encuentran:

| Módulo | Regla |
|---|---|
| Pacientes | Correo válido, fecha de nacimiento no futura y correo único. |
| Médicos | Cédula profesional única y especialidad existente. |
| Especialidades | Nombre único. |
| Usuarios | Correo único y relación válida con médico cuando el rol sea MEDICO. |
| Citas | Paciente y médico existentes. |
| Citas | Duración fija de 30 minutos. |
| Citas | No permitir fechas pasadas. |
| Citas | Impedir traslapes para el médico. |
| Citas | Impedir traslapes para el paciente. |
| Citas | Permitir citas consecutivas. |
| Citas | Las citas canceladas no bloquean disponibilidad. |
| Citas | Controlar las transiciones de estado permitidas. |
| Agenda | Respetar la zona horaria de Ciudad de México. |
| Reportes | Aplicar los criterios de agrupación y corte definidos. |

### 8.3. Manejo de traslapes y operaciones concurrentes

La validación de disponibilidad se realizará en la capa de servicios.

Para identificar conflictos se compararán los intervalos de las citas, considerando que cada cita tiene una duración fija de 30 minutos.

La condición de conflicto será:

```text
inicioA < finB AND finA > inicioB
```

Esta comparación permitirá detectar traslapes incluso cuando los horarios de inicio sean diferentes.

Las citas consecutivas estarán permitidas cuando el inicio de una coincida exactamente con el final de otra.

Las citas CANCELADAS quedarán excluidas de las comprobaciones de disponibilidad.

Las operaciones de programación deberán utilizar transacciones y una estrategia de protección frente a solicitudes concurrentes. La implementación deberá considerar que una transacción convencional, por sí sola, no garantiza evitar todas las carreras de concurrencia; será necesario definir y probar el mecanismo de protección correspondiente en PostgreSQL.

### 8.4. Gestión de estados

El estado inicial de cada cita será `PROGRAMADA`.

Las únicas transiciones permitidas serán:

```text
PROGRAMADA
    |
    |-------------------|
    v                   v
COMPLETADA          CANCELADA
```

Los estados `COMPLETADA` y `CANCELADA` serán finales.

La modificación de estados estará restringida a médicos autorizados sobre sus propias citas.

## 9. Manejo de errores y respuestas HTTP

La API utilizará respuestas HTTP consistentes para comunicar el resultado de las operaciones.

| Código | Situación |
|---|---|
| 200 | Consulta o actualización exitosa. |
| 201 | Registro creado correctamente. |
| 400 | Datos inválidos o campos requeridos faltantes. |
| 401 | Usuario no autenticado o token inválido. |
| 403 | Usuario autenticado sin permisos o sin pertenencia al recurso. |
| 404 | Recurso solicitado inexistente. |
| 409 | Conflicto por duplicidad, traslape o transición de estado no permitida. |
| 500 | Error interno no controlado. |

Se implementará un middleware centralizado de manejo de errores.

Los servicios podrán generar errores controlados que el middleware transformará en respuestas HTTP apropiadas.

Los errores internos no deberán exponer contraseñas, tokens, credenciales ni detalles sensibles de la base de datos.

Las consultas sin resultados devolverán HTTP 200 con una colección vacía cuando se trate de endpoints de listado.

## 10. Reportes y consultas especializadas

### 10.1. Volumen de citas por especialidad

El reporte agrupará el total de citas por especialidad médica.

La información se obtendrá relacionando:

```text
Appointment
     |
     v
   Doctor
     |
     v
  Specialty
```

Como la especialidad no está almacenada directamente en la tabla de citas, se utilizará una consulta SQL parametrizada mediante Prisma `$queryRaw`.

El reporte incluirá todos los estados de las citas:

- PROGRAMADA.
- COMPLETADA.
- CANCELADA.

El resultado permitirá identificar el volumen de citas asociado a cada especialidad.

### 10.2. Corte operativo diario

El corte diario devolverá la cantidad de citas COMPLETADAS y CANCELADAS correspondientes a una fecha específica.

Se utilizará `groupBy()` de Prisma Client sobre el modelo de citas.

La consulta filtrará el estado con `status in [COMPLETADA, CANCELADA]` y limitará `start_at` al rango del día solicitado, para excluir explícitamente las citas PROGRAMADA.

El cálculo del día deberá considerar la zona horaria `America/Mexico_City`, convirtiendo correctamente sus límites a instantes UTC para consultar los registros almacenados.

Los intervalos de consulta utilizarán inicio inclusivo y final exclusivo para evitar problemas en los límites del día.

## 11. Configuración, entorno y ejecución

### 11.1. Variables de entorno

La configuración se administrará mediante variables de entorno validadas con Zod.

| Variable | Propósito |

| `DATABASE_URL` | Conexión de la aplicación a PostgreSQL. |
| `TEST_DATABASE_URL` | Conexión exclusiva para pruebas de integración. |

No se permitirá utilizar la base de producción o desarrollo como alternativa para las pruebas de integración.

### 11.3. Inicio de la aplicación

La inicialización estará separada en dos archivos:

- `app.ts`: configuración de Express, middlewares, rutas y documentación.
- `server.ts`: inicialización del servidor HTTP y escucha en el puerto configurado.

Esta separación permitirá ejecutar pruebas HTTP con Supertest sin iniciar el listener de producción.

## 12. Pruebas y calidad del software

La estrategia de pruebas estará organizada en tres niveles.

### 12.1. Pruebas unitarias

Verificarán el comportamiento de funciones y servicios de manera aislada.

Se probarán especialmente:

- Validaciones de datos.
- Reglas de negocio.
- Transiciones de estados.
- Comprobaciones de disponibilidad.
- Autorización y pertenencia de recursos.
- Cálculos de fechas y rangos.

### 12.2. Pruebas de integración

Comprobarán la interacción de los servicios y modelos con PostgreSQL mediante Prisma Client.

Se utilizará una base de datos exclusiva para pruebas.

Se comprobarán:

- Creación y consulta de registros.
- Relaciones entre entidades.
- Restricciones de unicidad.
- Consultas de expedientes.
- Operaciones sobre citas.
- Reportes y agregaciones.
- Comportamiento de transacciones.

### 12.3. Pruebas HTTP

Se utilizarán Supertest y Vitest para comprobar los endpoints.

Se verificarán:

- Métodos y rutas.
- Códigos HTTP.
- Validaciones de solicitudes.
- Autenticación JWT.
- Autorización por roles.
- Restricciones de pertenencia.
- Respuestas de errores.

### 12.4. Verificación de calidad

El proyecto deberá pasar:

- Pruebas automatizadas.
- Typecheck de TypeScript.
- Validación del esquema Prisma.
- Build de producción.

No se considerará finalizada una funcionalidad únicamente porque su endpoint responda correctamente; también deberán verificarse sus reglas de negocio y restricciones de acceso.

## 13. Documentación de la API

Se utilizará Swagger UI con OpenAPI para documentar los endpoints.

La documentación incluirá:

- Método HTTP y ruta.
- Descripción de la operación.
- Parámetros de ruta y query strings.
- Estructura de los cuerpos de solicitud.
- Ejemplos de respuestas.
- Códigos HTTP.
- Requisitos de autenticación.
- Roles autorizados.

Swagger UI estará disponible mediante `/api/docs`.

Las rutas protegidas documentarán un esquema de seguridad OpenAPI `bearerAuth` de tipo HTTP, con `scheme: bearer` y `bearerFormat: JWT`, para permitir que los usuarios autorizados prueben los endpoints con JWT.

## 14. Consideraciones de implementación y evolución

La arquitectura se desarrollará de manera incremental, siguiendo el orden de dependencias entre los módulos.

Las etapas principales serán:

1. Configuración del entorno, Prisma y PostgreSQL.
2. Implementación del esquema de datos y migraciones.
3. Desarrollo de los módulos de pacientes, médicos y especialidades.
4. Implementación de autenticación y autorización.
5. Desarrollo de expedientes y relaciones entre entidades.
6. Implementación del módulo de citas y sus reglas de negocio.
7. Desarrollo de reportes de gerencia.
8. Pruebas integrales, documentación y preparación de entrega.

La implementación deberá conservar la separación de responsabilidades definida en este documento.

Los cambios en el esquema de datos deberán reflejarse mediante migraciones controladas.

Los cambios en los endpoints deberán mantener actualizada la documentación OpenAPI.

La arquitectura deberá permitir incorporar nuevas funcionalidades en el futuro sin obligar a modificar innecesariamente los módulos existentes.

## 15. Resultado esperado

Al finalizar la implementación, Clínica Salud Integral contará con una API RESTful organizada en módulos y capas, capaz de:

- Administrar pacientes, médicos, especialidades y cuentas de acceso.
- Consultar expedientes con el historial completo de citas.
- Autenticar usuarios mediante JWT.
- Restringir operaciones según los roles RECEPCIONISTA, MEDICO y GERENCIA.
- Aplicar autorización por pertenencia para proteger las agendas y citas de cada médico.
- Programar citas respetando las reglas de disponibilidad y duración.
- Consultar agendas médicas por rangos de fechas.
- Actualizar estados de citas de acuerdo con las transiciones permitidas.
- Generar reportes operativos para gerencia.
- Mantener la información persistida en PostgreSQL mediante Prisma ORM.
- Proporcionar endpoints documentados y verificables mediante Swagger UI.
- Mantener una base de código modular, tipada, comprobable y preparada para futuras aplicaciones consumidoras.

La arquitectura constituye la guía técnica para desarrollar el sistema. Su implementación deberá respetar los requerimientos, las reglas de negocio, el modelo entidad-relación y el modelo relacional establecidos en los documentos anteriores.
